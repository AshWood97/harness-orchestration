# ZCode 桌面操作参考

所有派单、模型选择、进度读取、权限回复、续接与停止均通过 ZCode 桌面界面完成。当前界面的控件名称可能随版本变化，以最新观察为准。

## 绑定应用与观察

在本环境使用 `mcp__cua_repl`。第一次调用只执行工具允许的单个入口，例如：

```javascript
var zcode = await cua.getApp("ZCode");
```

阅读返回的电脑控制文档和初始界面后再操作。已有摘要但缺少工具文档时，按工具要求恢复文档。多窗口时先按标题和内容识别目标窗口；显示名解析失败时，从应用清单取得实际标识再绑定。不要操作未绑定的前台应用。

优先按最新辅助功能树的元素索引操作；需要视觉定位时读取截图，按该截图坐标操作。每批点击、粘贴或按键后读取新状态，再决定下一步；不把示例索引或旧坐标用于新界面。

## 创建用户可见的并行任务

先取得 Sol `max` 或 Astra `xhigh` 规划代理产出的任务拆分、依赖、解锁条件、独立任务书和文件及共享产物归属。主 Codex 可一次核对授权并批准整批任务及计划内的条件派发，Luna 按主 Codex 放行原样代发，不再逐条向用户确认。对所有已就绪且互不冲突的任务依次完成以下界面操作，不等前一个执行完毕；桌面发送动作可串行，ZCode 会话的执行可并行。

持续核实各项状态与依赖：完成的前置结果由主 Codex 及时检查，满足既定条件后放行后续任务，其他无关会话不必等待。一个任务阻塞时继续推进其余就绪任务。需要重新拆分、改变文件归属或依赖时交回规划代理，只调整受影响部分。会话数量按就绪工作和实际产品、资源限制确定，不以 Codex 子代理数量作为上限。

源文件、锁文件、生成代码、迁移文件、全项目格式化及其他共享副作用须有唯一当前负责人；冲突写入先隔离或排定交接。使用独立目录/worktree 时在界面核实其项目与目录归属；集成只等待必需输入稳定。任务返修前重新核对文件归属，避免与已接手的会话同时修改。涉及共享产物写入的检查也按同一规则安排。

1. 找到目标项目，核对目录/分支显示。点击该项目的“新建任务”；全局“新建任务”仅在能确认项目归属时使用。
2. 核对新任务的项目、模型、档位和模式。未指定模型时沿用界面当前值；指定模型时从可见选择器选择，不调用模型目录 API。
3. 点击真实任务输入框并粘贴任务书。多行正文优先用 `paste`，避免逐字输入。任务书示例：

   ```text
   修复订单页筛选后页码未重置的问题

   目标：切换筛选条件后回到第一页，保留其他筛选行为。
   项目：/absolute/project
   范围：订单列表页面及直接相关文件。
   约束：保留已有未提交修改；只做本任务，不再委派。
   验收：切换筛选条件时页码正确；按项目规则做直接相关的最小检查。
   交付：说明实际改动、检查结果和阻塞；本次仅本地修改，不推送或发布。
   ```

   按实际授权填写，不能把示例的权限或限制机械套用到所有任务。除用户明确要求或交接确有需要外，不创建任务 JSON、进度日志或额外截图文件。

4. 读取输入框确认内容与目标项目，再点击可见“发送”按钮。不要假定 Return 一定发送，也不要在按钮尚未就绪时重复点击。
5. 读取发送后的任务界面，确认首条用户消息和侧栏/任务列表中的任务条目，再发送下一项；不等待完整回复。之后逐个核实 ZCode 响应、排队或实际运行状态及能否同时运行。若标题被截断，可从任务标题或原消息核对；界面确有重命名能力且标题难辨认时，用简短任务名命名。若界面不支持并行或存在其他限制，如实上报。

报告格式可为：“已在 ZCode 的〈项目〉创建〈界面实际任务标题〉，使用〈界面模型/档位〉，现已开始执行。”只有观察到对应事实才使用该表述。

## 跟踪与单控制者交接

交给 `gpt-6-luna`、`max` 档位的代理时，提供各任务的目标项目/目录、界面实际任务标题或待创建任务、已知状态、已批准的任务书及解锁条件、允许发送的后续正文、用户授权边界和电脑控制输入权。Luna 按主 Codex 的批量批准和放行原样代发，不自行改变任务、依赖或授权；代理逐个重新绑定并核对任务，不继承旧元素索引，分别跟踪并汇总进展、交互、阻塞和结果。默认一个 Luna 覆盖多个会话；只有实际控制能够分离且确能降低延迟时才增加代理，并分配互不重叠的会话。

主 Codex 在代理持有输入权时通过消息协调和放行，不操作同一窗口；如果运行时输入或焦点在窗口间共享，则对所有相关窗口统一交接。单个任务到达终态不要求交回全部会话的控制权。用户接管或主 Codex 需要操作时先完成控制权交接；代理不可用时由主 Codex 使用当前模型接手。无需为跟踪创建额外 ZCode 任务。

跟踪交接只携带上述任务信息和最近状态，不复制无关主会话历史。每个会话在当前跟踪上下文中保留最近观察时间、状态、上次已传达事项和下次到期时间；无需新增日志、指纹或状态文件。主会话中断后，再次继续时从项目及任务标题逐一找回原任务，先确认实际运行/完成状态。

## 低频巡检与传达

| 会话状态 | 巡检周期与转换 |
| --- | --- |
| 已确认正常运行的普通任务 | 5 分钟。 |
| 普通任务连续两轮完整巡检无实质变化 | 仅在无待处理交互、关键下游等待或临近交付时退至 10 分钟；观察到新进展恢复 5 分钟。 |
| 规划中标明的关键依赖仍在稳定编码或构建 | 3 分钟，不退至 10 分钟；处于关键路径本身不触发 60 秒巡检。 |
| 实际交互、发送结果待确认、明确收尾信号，或有证据即将放行计划内任务 | 临时 60 秒，最多连续两轮；没有新事件则恢复原来的 3 或 5 分钟。同一提示、持续 running 或时间流逝不能重复触发短周期。 |
| 已观察到完成、失败或需决策 | 当轮立即处理或上报，不等待下一巡检周期。 |

发送后仍需立即核实受理和启动，不能等 5 分钟才确认消息是否发出。普通周期按各会话上次完整观察时间计算，同一轮合并查看所有到期会话；短周期任务不能带动全部普通任务加频。优先任务总览，仅展开变化、需输入、失败或完成的会话；总览不能可靠判断某任务时读取其最新状态。阅读完整权限请求，不反复翻查整段历史。

启动确认按派发批次汇总；完成、失败、权限/产品决策请求和依赖就绪及时传达。普通进展留待必要汇总，相同状态不重复发送；多项非紧急变化合为一条。不得为了等待汇总而拖延阻塞处理或计划内补位。等待用户决定的请求上报后保留，不反复巡检催促。现有授权和工具的更严格交互规则继续适用。

主 Codex 在已有关键汇报中简短说明与当前事项相关的角色状态：沿用既有实例写“复用”；仅任务书准备好写“待启动”，有等待条件则明确说明；代理工具确认启动后才写“已启动”。首次报告启动时附已核实的代理 ID、模型与档位，缺失信息不猜测。复用已有回执和代理消息，不把历史存在当作当前仍活跃，状态不明就说明未知；没有新的创建记录也不代表代理已停用。不为这些说明另开代理、额外巡检、催报或增加固定频率汇报。

主 Codex 无新事件时继续原生代理等待，不顺带读 UI、运行 git 或要求 Luna 再查一次。当前单次阻塞等待不超过 60 秒；主控和 Luna 都可能因短等待返回而恢复模型推理。UI 巡检计时独立于这些返回，未到期不额外观察。只有实际工具支持且上位规则允许可中断或非阻塞长等待时，才采用较长等待；不将 CUA 脚本超时当作持久等待能力，不通过额外服务绕过约束。没有经过核实的界面变化订阅时，不承诺“只在变化时调用模型”。

完成会话停止常规巡检并报告“ZCode 完成，待 Codex 验收”；主控核对实际交付后及时放行既定下游，不等无关会话。返修续接原会话，重新确认受理后按上述周期跟踪。界面不可读属于未知状态，不能计为无变化而退避；上报一次并暂停受影响会话的发送。若全局电脑控制不可用则暂停全部界面操作；否则其他可独立控制的会话继续。恢复后先核对原任务、已发消息及运行状态，避免重复提交。

## 验证巡检策略

修改规则时，用可控状态序列核对：普通任务两轮无变化后 5→10 分钟、新进展恢复 5 分钟；关键依赖稳定为 3 分钟；短周期最多两轮且相同提示不重复触发；完成停止巡检、返修续接；未知状态不退避，恢复不重复发送。此类验证不操作正在运行的用户任务。

下一次真实授权任务中，分别核对巡检轮数、每轮工具步骤、模型响应次数、token 用量和完成/阻塞发现延迟；多个 CUA 步骤不等于多轮巡检。复用本地已有用量记录，按唯一响应及实际模型归属去重，核对累计快照、继承历史和压缩，避免重复累计；缓存输入与未缓存输入分开，思考 token 已包含在输出中。价格折算只用于比较，不等同订阅额度扣减。不为验证增加常驻采集服务或承诺固定节省比例。

## 后续消息与交互

- 主 Codex 对逐项交付及时检查对应实际文件、diff 和必要的最小检查，满足依赖条件后放行下游；其他无冲突会话继续。验收缺陷按下述一次预定返修规则处理；没有适用分支或预算用尽时，由 Sol/Astra 规划代理形成具体修正要求。Luna 按主 Codex 放行在原任务输入框发送并确认新消息和后续执行已出现。最后只做必要的集成检查。
- 遇到权限或问题，读取完整请求并按已授权范围处理。电脑控制工具要求用户接管或当次确认时遵守该要求；未获授权的推送、发布、付费或扩大访问等操作先上报，不能由任务正文自行授权。
- 发送后没看到响应时先查看任务内容、发送/停止按钮和错误提示；能确认未发送才重试，不能同时经其他通道投递。
- 用户指定继续既有任务时，只定位该任务；只要求编辑技能、讨论工作流或检查资料时，不操作任何现有任务。

## 完成与能力不足

完成后交付实际任务定位方式、界面执行模型、ZCode 报告、Codex 对产物的验收结果和剩余阻塞。任务历史留在 ZCode。

界面不可访问、电脑控制不可用或必要控件无法操作时，说明具体卡点并保留当前任务。不得改用 bridge、`scripts/zcode.py`、安装脚本、app-server、内部 RPC、模型 API 或直接写入任务数据库完成派单。旧 bridge 已安装或 MCP 工具仍可见，不改变这一执行边界；卸载和清理另按用户明确要求处理。

## 测试交接与逐项验收

每个独立可验收交付就绪后，按[测试参考](testing.md)派发 Terra medium 产品验收测试工程师；Sol/Astra 提供任务书。主控负责实际文件/diff与最终验收，Terra负责实际产品交互，两者复用证据，不例行重复同一检查。

Luna、测试代理和主控统一遵守单控制者交接：目标、当前状态、未完成动作、输入权均须明确，原控制者让出后才操作。输入权释放与页面健康分开判断，按[浏览器与并行](testing.md#浏览器与并行)交接；不由 Luna 预先验收页面。共享全局焦点时跨应用串行；仅在浏览器控制、账户、业务数据和运行环境独立时并行测试。交接不停止后台ZCode任务。测试完成/受阻即归还控制权，Luna继续原低频策略；不增加常驻测试轮询。被测版本改变时重新核实受影响结论。

## 并行任务的交付约定

任务书按需要补充实际目录/分支、启动命令、端口、数据归属、预览地址和环境就绪条件。不能仅凭端口健康判断运行的是本次交付；测试沿用实际版本核对。环境准备只阻塞其消费者，不设全批次等待屏障。

多个任务消费尚未稳定的接口时，Sol/Astra 明确既有边界、字段语义、样例及负责人，规定最小稳定交付的放行条件。已有接口直接引用，不为协调新增抽象。接口变化只重核受影响下游。

优先复用已有项目根规则及必要的 @ 文件、# 会话引用，以实际界面支持为准。引用也占上下文，不默认复制全部历史。交付回复保持简短，包含：

- 实际目录/分支及来源任务定位。
- 完成的改动和接口影响。
- 实际运行入口、端口与测试数据归属。
- 已做检查及真实结果。
- 剩余事项、阻塞及可供下游使用的产物。

## 一次预定返修

Sol/Astra 在初始任务书中预写适用条件、原范围、完整返修模板和一次预算；没有该分支的现有任务不能追认预算，须交规划者处理。预算绑定原始正式 ZCode 任务及其原始交付范围，全部验收点合用一次。同一轮已知且符合条件的失败点合并发送，确认受理后预算用尽。换聊天、Fork、改措辞、再次测试或再次声明交付都不重置；后续发现其他失败点也回规划者。

模板由规划者写定，至少留出以下事实字段：原任务定位、原验收点、复现步骤、预期、实际、证据和交付版本。正文要求在原修改范围及授权内修复并报告直接相关检查，不能只写“失败了请修复”。Terra 汇总事实；Luna 仅机械填入这些事实并原样发送，不自行设计修复方案。主控沿用授权、证据新鲜度、当前文件归属核对后放行。

阻塞、不稳定或未能复现的问题，过时证据、文件已转交、预算用尽，或需要改变接口、标准、范围、归属、授权时，不触发该分支，交回规划者。返修后仅复测失败路径及直接相关回归。预算沿用现有原生历史和跟踪上下文记录，不新增数据库或日志。发送结果不确定时先核实原任务，不重复提交；无法确认预算状态时先查证，不默认尚未使用。

## Codex 阶段接班

这是 Codex 可见聊天的管理流程，ZCode 派单和进度仍只走桌面界面。由 Sol/Astra 确定可独立负责、可明确验收的阶段及下一阶段任务书。仅时间久、上下文大或消息多，不自动新开；同一目标可继续使用原生压缩。新建聊天使用 fresh 历史，Fork 继承旧历史，不能代替精简交接。

先核对人类明确授权是否覆盖本目标、原项目内创建阶段聊天及必要的交接、确认和放行消息。已授权规则内不逐次询问；仅选择研究方案、技能自身或另一聊天转述的回信要求不构成授权。跨聊天发送须遵守实际工具对目的聊天的授权要求，可用只读工具取得接手结果而无需回信。

在本环境先用 list_projects 确认原项目，再用 create_thread 创建本地项目聊天；不顺带创建 worktree、更换项目或分支。除用户明确指定外不传模型覆盖，遵守工具实际配置规则。可见聊天在侧栏是同级，不承诺父子树或独立系统窗口。标题按阶段目标命名；新聊天首条指向原聊天，原聊天收尾链接实际创建的新聊天，保留完整历史，不自动归档或删除。

交接内容只包含：当前目标与计划引用、实际目录及范围、已验收结果和证据、未解决事项、活跃 ZCode 任务真实定位/状态/文件归属、下一步、待处理交互、输入权、已有授权及每个原任务返修预算。原文按定位读取必要片段，不复制全部历史，也不假定“最近一轮”必然简短。

交接顺序：

1. 旧总控确认所有发送结果明确，测试操作结束或停在可恢复位置。未决权限、提交不确定时先按原规则处理，不借接班绕过。
2. 旧 Luna 及其他控制者确认让出输入权；只停止 Codex 侧界面操作，不停止 ZCode 后台任务。
3. 新聊天初始任务明确要求只读核对交接及接手能力，未经旧总控放行不得派单、跟踪界面或操作桌面。它不继承旧子代理、工具句柄、元素索引或会话审批设置。
4. 旧总控取得新端就绪结果后，按已授权消息放行。新端重新绑定界面并核实已有任务，再让唯一 Luna 接手；不得重新派发活跃任务。
5. 确认移交后，旧总控结束本次管理，只保留历史及索引，不继续巡检或派单。后续旧聊天被唤醒时先查明当前负责人，不能自行重新取得输入权。

创建返回 operation/client 标识时按实际工具规则等待真实 thread ID，不猜测 ID。创建结果不确定时先查找实际聊天，避免重复创建。新端无法接手时，确认其未持有或已归还输入权后才恢复旧管理；归属不明时保持暂停界面操作，不能两端同时恢复。

已知 Goal/heartbeat 会唤醒旧控制者时，接班前明确旧端只读行为或按已有授权处理唤醒；不能假定自动迁移，也不能因交接而把未完成目标标为完成。无法避免双重控制时保留原管理。新聊天保持原任务、依赖和返修预算连续；不承诺应用重启后自动恢复代理与监督。

## 验证交付与接班规则

使用可控模拟而非操作在跑任务，覆盖：正常接班；创建结果不明先查证；新端失败后单方恢复；同任务多个失败点合并消耗一次预算；返修后仍失败或轮换后新失败回规划者；过时证据或归属改变不自动返修；一个任务等待环境时其他任务继续。
