# Codex ZCode

独立规划代理负责制定任务计划和任务书；主 Codex 使用当前模型负责协调、核对授权、派发决定、必要决策和最终验收；ZCode 在桌面应用的真实会话中执行；Luna 可代发已定任务并跟踪各会话、传达信息；Terra medium 产品验收测试工程师验证可独立验收的交付。使用当前运行时的原生电脑控制工具操作 ZCode，像用户平时一样选择项目、点击“新建任务”、在输入框填写任务并发送。任务、回复、工具执行和后续修改应保留在 ZCode 原生历史中，让用户能看到操作并自行打开记录。

## 唯一执行入口：ZCode 桌面界面

- 通过当前运行时的电脑控制工具（本环境为 `mcp__cua_repl`）绑定 ZCode 应用和目标窗口。首次调用及后续操作遵守工具当次返回的文档，不猜测 API、元素索引或固定坐标。详细操作见[桌面操作参考](references/operations.md)。
- 不调用 `codex_zcode` MCP、bridge 脚本、app-server、无界面 CLI、内部 RPC 或直连模型 API 来派单、续接、批准权限或读取执行进度；桌面能力不足时报告阻塞，不自动回退这些通道。
- 不通过修改 ZCode 数据库、任务索引、会话文件或模拟事件来创建历史。只有界面实际创建并显示的任务，才能报告为已派发。
- 本技能不负责卸载旧 bridge、更改 MCP 配置或停止既有任务。用户只要求修改技能时，只修改技能文件，不启动或接管 ZCode 任务。旧实现来源保留在[历史运行时资料](references/runtime.md)，不作为执行指引。

## 规划与分工

- 每次均由独立规划代理制定任务计划和任务书：默认明确指定 `gpt-6.1-sol`，推理档位 `max`；复杂或高风险任务明确指定 `gpt-6-astra`，推理档位 `xhigh`。主 Codex 不参与制定或补写任务规划，即使主模型与规划模型相同也不例外；主 Codex 可转交用户要求和必要上下文，并检查任务书是否完整、符合授权，发现缺口交回规划代理修订。
- 规划代理或指定模型、档位不可用时，说明具体阻塞并停止派单；不由主 Codex 代为规划，不假称调用成功，也不静默更换模型或档位。
- 规划代理一次梳理任务依赖、派发顺序和明确的解锁条件、可并行工作、文件与共享产物归属及验收条件，生成有实际交付物的独立任务书。有多项互不冲突的工作时，尽可能一次派发全部已就绪任务，不预设一个任务或固定并发上限；ZCode 会话数量取决于就绪工作和实际产品、资源约束，不受 Codex 子代理槽位数机械限制。任务天然不可拆分时不强行拆分。
- 持续补位：主 Codex 按既定条件及时核实前置结果并放行新就绪任务，不等待无关会话完成；单项阻塞时其余无冲突任务继续。新增拆分、修改范围、归属或依赖交回规划代理，只修订受影响部分。
- 每份任务书包含明确目标、项目/执行目录、必要背景、允许修改范围、禁止事项、验收条件，以及用户已授权或未授权的推送、发布、付费生成等操作。ZCode 不会自动获得 Codex 的全部对话。任务正文首行用简短中文概括目标，方便 ZCode 生成可辨认的历史标题；不要求额外 JSON 文件或 bridge task_id。
- 同一项目可通过桌面创建多个独立 ZCode 任务会话，并行执行已就绪工作；界面操作按实际能力逐个完成，已启动的会话不必等待前一个完成再启动下一个。根据界面核实每个会话是否已启动及能否同时运行；遇到产品或资源限制时报告，不虚报并行。
- 同目录中仅在修改范围、锁文件、生成代码、迁移文件、全项目格式化等共享写入和其他副作用互不冲突时并行。规划代理为共享写入指定唯一当前负责人，有重叠或依赖时安排可在界面核实归属的独立目录/worktree，或按依赖顺序执行；集成只等待必需的输入稳定。返修前重新核对文件归属，其他会话及主 Codex 不同时修改当前负责人负责的文件。
- 默认由一个明确指定 `gpt-6-luna`、推理档位 `max` 的代理跟踪多个桌面任务、汇总并传达信息；实际控制能够分离且能降低延迟时才增加 Luna，明确各自负责的会话。主 Codex 可一次核对授权并批准一批定稿任务及计划内条件派发，Luna 在收到放行后通过界面原样发送任务书或已确定的后续消息，无需逐条再次询问用户；Luna 不自行决定任务、修改正文或依赖、扩大授权或再委派。运行时不支持指定模型或档位、代理不可用或停止时，主 Codex 说明并使用当前模型接手。
- 每个 ZCode 窗口同一时间只有一个电脑控制者；若运行时输入或前台焦点是全局共享的，跨窗口也要串行操作。主 Codex 与跟踪代理交接目标项目、任务标题、当前界面状态和输入权，不能互相干扰；界面操作串行不妨碍已启动任务并行执行。主 Codex 其余职责始终使用当前模型，不为本流程更改主模型或档位。

## 产品验收测试工程师

- 每个可独立验收的交付默认自动触发技能专用逻辑角色 `zcode_tester`，小改动可按规划合并。固定 `gpt-6.1-terra` / `medium`，使用默认代理、显式模型与档位、`fork_turns="none"`；不要调用现有固定 max 的 `tester` 或修改 Native 角色及全局配置。具体派发提示与输入输出见[测试操作参考](references/testing.md)。
- Sol/Astra 制定测试任务书和返修要求；测试者在既定范围内验证用户可见结果、必要边界和相邻回归，可调整操作路径，不改需求、源码或验收标准，不再委派或向 ZCode 派单。允许任务书授权的可逆测试交互。纯后台及文档变更采用适用的验证方式，不机械启动浏览器。
- 可测环境和依赖就绪后即测试，其他无冲突 ZCode 会话继续；共享输入权先与 Luna 交接。仅在控制能力、账户、数据和运行环境均独立时并行测试多个交付。完成或阻塞即返回，不承担常驻跟踪。指定模型、档位或工具不可用时报告测试阻塞，不静默替换或冒充通过。
- 主 Codex 结合测试证据与实际变更最终验收，不例行重复全部界面测试。按代理 ID 和职责分别统计主控、Luna 跟踪与 Terra 测试用量，即使主控也使用 Terra；低频跟踪策略保持适用。

## 新建、模型与历史

1. 在 ZCode 侧栏找到用户指定项目，核对实际目录。为每个已就绪任务在该项目中点击“新建任务”；用户明确要求续接时打开指定历史任务，不把新目标塞进无关旧会话。
2. 从界面读取当前模型、档位和模式。用户未指定时保留 ZCode 新任务当前选择；明确指定时在模型选择器中选择并核对。Codex 的规划/跟踪模型与 ZCode 执行模型分别报告，不修改 ZCode 持久默认设置。
3. 对每项任务将对应任务书粘贴到真实输入框，读取最新界面确认正文、项目与模型，再点击发送。确认用户消息已出现、侧栏或任务列表存在该任务后，继续发送其他已就绪任务，不等待完整回复；后续核实各任务是否排队或实际运行。界面只显示模型标签时，按该标签报告，不推测隐藏 provider ID、用量或服务商。
4. 向用户报告每个任务的实际项目、历史任务标题、界面模型/档位和启动状态。若界面提供任务链接或 ID，可一并交付；未提供时用“项目 + 任务标题”定位，不制造链接。

## 跟进、续接与验收

- Luna 对正常执行的普通任务每 5 分钟巡检；连续两轮无实质变化且无交互、关键下游或临近交付时退至 10 分钟。关键依赖稳定执行时每 3 分钟巡检；实际交互、发送结果待确认或明确收尾信号才临时改为 60 秒，最多连续两轮。详细触发、恢复和去重规则见[低频巡检与传达](references/operations.md#低频巡检与传达)。一轮合并检查多个到期会话，不按窗口分别等待；发现完成后及时验收和补位，不等待整个批次。
- Luna 按批次确认启动，及时上报完成、失败、权限/决策请求和依赖就绪；相同“仍在执行”不重复传达。主 Codex 无新事件时继续等待，不附带读取界面、查 Git 或催报；文件复核集中于新交付、依赖放行和必要验收。跟踪上下文只携带任务定位、最近状态、授权及待发送内容，避免重复传递完整历史或界面文本。
- 巡检周期与模型唤醒分别统计：当前单次阻塞等待不超过 60 秒，短等待返回仍可能产生推理。仅当实际运行时明确支持且上位规则允许时，采用可中断或非阻塞长等待；不能通过长脚本或后台服务绕过限制。不要把 5 分钟巡检描述为 5 分钟仅调用一次模型，不承诺固定节省比例、虚构进度百分比或主会话结束后的常驻跟踪。
- 权限请求先展开完整内容，按用户授权和电脑控制工具的实际规则决定；不能只凭摘要点击允许，也不因方便改成“始终允许”或降低审批模式。需要用户决定时保留请求并上报。
- 修正与继续执行在原任务输入框发送后续消息。发送结果不确定时先读取会话，确认消息是否已出现，避免重复提交。超时或出错不自动新建任务、换模型或重做已受理的外部操作。
- 只在本次授权需要时通过任务内的可见控件停止执行，并确认界面停止；不停止或接管用户的其他任务。
- ZCode 逐项交付后，主 Codex 检查对应实际文件/diff、产物和必要的最小检查，及时核实下游所需输入；无冲突会话继续运行。会写共享产物的检查纳入文件归属和时序，最后只做必要的集成检查。区分“ZCode 报告完成”与“Codex 已验收”；具体验收缺陷交规划代理制定修正要求，再由 Luna 在原历史任务内发送。完成后保留任务及历史，不自动归档或删除。
