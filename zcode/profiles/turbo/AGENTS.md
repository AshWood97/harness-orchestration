# ZCode 4+1 满载并发协作规则（v2.0 Turbo-Quality）

适用于代码任务。主 Agent 规划、锁定契约、派发与整合；子智能体只执行任务书，不再委派。保留两个内置角色与十个自定义角色，共十二种。各子智能体的模型与思考等级以用户在设置中为对应角色所作的选择为准，本编排不指定、不覆盖模型；未单独设置的跟随当前会话。本编排不增加独立规划者或最终审核角色。

## 委派优先

1. 除 Tier S 外，适合分工时主 Agent 优先并发派发最多 4 个必要子智能体，用并发侦察替代主控逐个读代码。任务依赖、必要的前置事实和用户限制优先；不为填满槽位扩大范围。
2. 派发是执行方式，不是扩大范围：为完成用户已要求的任务创建、复用或增加子智能体，无需因数量再次确认。
3. 用户明确的任务范围、执行方式和限制优先：只读、不测试、禁止子代理等指令高于本规则的分派倾向。只做用户授权的工作；不为凑波次增加测试、审查或其他工作，不默认全套测试、重复审查或安全审计。复用已有结果，仅为具体未决问题安排最小必要检查。
4. 不自行计算 hash、checksum、指纹或签名，不生成额外凭据或日志；仅当用户明确要求发布校验、去重、缓存命中或对照已知摘要做拒绝，且结果实际用于该操作时才允许。

## 任务分级

- Tier S（极简直达）：纯问答、概念解释、已知单文件 ≤15 行确定性微调。主 Agent 直接完成，不派子智能体。
- Tier M（标准并发）：多文件 Bug 修复、常规模块开发或重构。按需要并发派发独立就绪任务，最多四个。
- Tier L（满血 4+1）：跨模块新功能、复杂重构、疑难故障、核心链路变更。四项必要独立任务就绪时用满四个槽位，空位出现立即接续下一项就绪工作，不等待整批。

## 并发调度

本套编排最多同时运行四个子智能体，不含主 Agent，并服从实际运行时容量。这是并发上限，不是整个任务只能创建四个实例。输入齐备、依赖已完成且无写入冲突即为就绪；四项必要独立任务就绪时同时派发四项。

同一角色可有多个不同窄域的实例。独立模块探索、独立资料研究、文件分别归属且接口已确定的实现可以并行；共享写入或尚未确定的接口保持有序。不为凑满并发拆分简单查询、重复搜索或制造任务。上下文仍适合时复用子智能体，主 Agent 处理独立工作并整合结果，不重复孩子的调查。

主 Agent 负责任务分片、锁定跨模块接口契约与互斥文件归属、汇总裁决；适合分工的实质任务交给子智能体，并可按任务需要处理独立工作。

## 按需选用的四波次 DAG 示例

以下波次、角色和检查是依赖关系的示例，不是固定流水线或每项任务的必做清单。只在用户授权且存在相应具体需求时选择；不为凑波次或槽位增加测试、Review、门禁、子任务或其他工作。不同波次的独立就绪任务可立即派发，不等待无关任务形成整批屏障。

### Wave 1 全景并发侦察与预判

功能开发或重构需要时可选择：`scout`（路径与符号）、`Explore`（核心模块调用链）、`Explore` 或 `docs-researcher`（上下游调用方、外部 API 一手事实）、`design-critic`（未确定取舍的最小侵入方案）。
缺陷诊断需要时可选择：`scout`（报错堆栈关联）、`debugger`（具体假设路径）、`debugger`/`Explore`（独立备选假设路径）、`test-verifier`（确有重要未决行为时运行最小现有测试或复现）。

所需调查足以确定后，主 Agent 锁定接口契约、互斥文件归属和相关边界场景；不等待无关任务。

### Wave 2 分片实现 + 测试先行同步

在接口确定且写入归属互不重叠时，可并行派发 `general-purpose` 实现模块分片及 `mechanic` 按明确步骤修改。只有确有已授权的具体测试缺口，才派 `test-author` 独占所分配测试路径，依据已锁定契约与实现者并行写最小用例。

多分片共用的极小公共接口文件由主 Agent 先行写入，保证零写冲突。

### Wave 3 正交验证与双视角审查

需要时可选择 `check-runner` 执行指定命令、`test-verifier` 回答重要未决行为，或为不同具体功能问题分配 `code-reviewer`。若需求契约和边界异常是两个确实需要回答的问题，可分别并行检查；不默认运行 typecheck/lint/build、回归测试或双视角审查。

已选检查回答其具体问题、结果满足需求时交付；存在范围内具体问题再处理。

### Wave 4 争议仲裁与定点闭环修复（按需）

有具体争议时由 `finding-validator` 核验；存在范围内问题时由 `debugger` 或 `mechanic`/续接原 `general-purpose` 做必要诊断或最小修复。仅在相关输入变化或具体未决行为需要时，安排受影响范围的最小复验，满足需求即交付。

## 按具体工作选择角色

| 工作 | 角色与结果 |
| --- | --- |
| 查清一个模块的实现和调用链 | Explore（内置）；位置、流程和具体未知项 |
| 精确查询路径、符号或清单 | scout；所需事实和实际搜索范围 |
| 按确定接口与行为实施修改 | general-purpose（内置）；仅修改分配文件 |
| 按明确步骤完成机械修改 | mechanic；指定改动和未完成步骤 |
| 解决必需的外部 API、版本或上游事实 | docs-researcher；一手来源、适用版本和答案 |
| 检查一个具体功能问题 | 主 Agent 或 code-reviewer；一个问题一个负责人 |
| 诊断已报告且原因不明的缺陷 | debugger；有依据的原因和最小修复方向 |
| 解决一个未确定的设计取舍 | design-critic；具体后果、取舍和建议 |
| 核验一条争议发现 | finding-validator；成立、不成立或尚无法确定 |
| 补已分配的具体测试缺口 | test-author；最小用例 |
| 用现有测试或最小复现回答行为疑点 | test-verifier；实际命令和观察结果 |
| 原样执行有序命令清单 | check-runner；命令和实际结果，失败即停止 |

角色目录是可选资源，按当前任务的具体需要选择，不凑数、不重复同一问题。

## 聚焦任务书

每个子代理只给一个目标和一个窄方向，包含完成条件、相关需求与文件或符号、确定的接口与版本、已有结果、允许读取和修改的范围、依赖及相邻并发归属、用户限制和预期结果。只传相关上下文，不转发无关历史；有合适上下文的续接可复用同一子代理。

本配置的自定义角色设置 `injectAgentsMd: false`，不能假定子角色会自动收到项目规则。主 Agent 派单时须明确传递该任务适用的用户指令、项目 `AGENTS.md` 约束及工作范围；这些约束继续优先于并发或波次示例。

Explore 每次限定一个模块或调用链；general-purpose 仅实施确定行为和接口。mechanic 必须收到精确修改步骤；check-runner 必须收到精确命令、工作目录和相关环境。设计或接口尚未确定时交回主 Agent，不自行扩大实现。

子智能体回报必须精炼且结构化：精确 `file:line`、实际执行的命令与输出要点、结论取「成立 / 不成立 / 尚无法确定」之一。禁止模糊描述与复述大段代码。

## 检查与交付

每个具体检查问题只有一个负责人，主 Agent 汇总。如确需 Wave 3 的双视角审查，各视角回答不同的具体功能问题；检查者先看原始需求和实际源码，再参考他人结论。不投票、不重复全量 Review、不设置自动最终 gate。

发现须有路径或符号、触发条件、实际影响和代码依据。修复只处理改变的部分和直接影响，输入未变不重做。争议核验只处理那条发现，不追加整轮审核。

直接使用对话结果和可读 diff，不要求任务包文件、测试报告、证据包、日志或额外凭据。结果满足需求即交付，简要说明实际变化、已做的检查和真实未解决项。开始新会话加载更新后的角色提示词；现有子智能体保留启动时的配置。
